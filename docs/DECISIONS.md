## 2026-11-06 — фаза 2, каркас

### 1. Нативное приложение: Swift 6 + SwiftUI, значок через `MenuBarExtra`
- **Почему:** лёгкое, выглядит как часть macOS, всё нужное есть в Xcode, ноль сторонних библиотек.
- **Альтернативы:** Python + `rumps` — нужен Python, менее надёжные уведомления и автозапуск, нет пути к виджету.
- **Источник:** паспорт, раздел 8; сигнатуры `MenuBarExtra(_:systemImage:content:)` и `.menuBarExtraStyle(.menu)` сверены по SwiftUI.swiftinterface в macOS SDK 26.5 (Xcode 26.6).

### 2. Логика — в локальном пакете `Packages/IPCheckCore`, приложение — в `App/`
- **Почему:** логику можно тестировать командой `swift test` за секунды, без сборки и запуска приложения. Приложение остаётся тонкой оболочкой.
- **Альтернативы:** тесты внутри проекта Xcode — медленнее, тянут интерфейс.

### 3. Проект Xcode генерируется XcodeGen 2.45.4 из `project.yml`, `.xcodeproj` в git не хранится
- **Почему:** `project.yml` — 60 читаемых строк вместо огромного служебного файла Xcode, в котором трудно увидеть изменения и легко получить конфликт.
- **Альтернативы:** хранить `.xcodeproj` в git.
- **Источник:** XcodeGen 2.45.4, Docs/ProjectSpec.md (разделы Target, Local Package, Scheme).

### 4. Подпись — локальная (ad-hoc), без Apple ID
- **Почему:** бесплатно и без входа в аккаунт. Проверено: сборка подписывается и проходит `codesign --verify --strict`.
- **Проверено 2026-11-06:** macOS распознала приложение с локальной подписью и показала запрос на уведомления (журнал `usernoted`: «Sending request for permission»). Риск «уведомления недоступны без Apple ID» не подтвердился.
- **Особенность:** если запрос закрыть или отказать, macOS отвечает на него ошибкой «Notifications are not allowed». Это учтено: `NotificationPermission.afterRequestError` берёт решение, сохранённое системой, и покрыто тестами.
- **Альтернативы:** бесплатный Apple ID в Xcode (Personal Team). На Mac уже есть сертификат разработчика, но он выпущен на **другой** Apple ID — без разрешения владельца его не используем.

## 2026-11-06 — этап 2, «Есть ли интернет»

### 13. Проверка связи — HTTP-запросы со строгим ответом, а не «открылось ли соединение» (согласовано с владельцем)
- **Почему:** VPN-программа владельца (весь трафик идёт через её интерфейс `utun4`) сама отвечает на открытие любого TCP-соединения. Проверено: соединения с зарезервированными несуществующими адресами `192.0.2.1`, `198.51.100.7`, `203.0.113.9` «открывались» за 16–23 мс. HTTP-запросы к тем же адресам проваливаются, а к настоящим служебным адресам — проходят.
- **Адреса:** Россия — Яндекс `http://ipv4-internet.yandex.net/api/v0/ip` (код 200 и IP в тексте), запасной VK `HEAD http://vk.com/robots.txt` (код 200); зарубеж — Google `http://connectivitycheck.gstatic.com/generate_204`, запасной Cloudflare `http://cp.cloudflare.com/generate_204` (код 204).
- **Строгость:** переадресации не выполняются (по документации URLSession: `nil` в `willPerformHTTPRedirection` отдаёт сам ответ 3xx), поэтому страница входа в гостиничный Wi-Fi не сходит за интернет. Правило ответа — `ProbeExpectation`, покрыто тестами.
- **Цена:** зависимость от DNS (если DNS не работает, сайты не открываются — это честный разрыв); трафик около 15–20 МБ в сутки вместо 5–15.
- **Альтернатива:** проверка «напрямую мимо VPN» — показывает домашний интернет, но не видит проблем VPN; с частью VPN-программ обход не работает. Отложена до этапа 5 (сервер NL).

### 14. Простой HTTP разрешён точечно для четырёх проверочных адресов
- App Transport Security по умолчанию запрещает простой HTTP. Исключения — только для этих доменов (`App/Info.plist`), данных туда не отправляется, проверяется код ответа. Модуль Б («HTTPS везде») — осознанное исключение с причиной.

### 15. Быстрое подтверждение разрыва
- После неудачной проверки, пока разрыв или «частично» не решены, следующая проверка — через 1 с (а не через 5). Таймаут проверки — 2 с (живые серверы отвечают за 0,05–0,45 с). Итог: разрыв определяется примерно за 14 с, как обещано в паспорте.

### 16. Что считается потерями
- Потери — случайные сбои. Неудачи, из которых сложился разрыв или «частично», в потери не идут. Свежие неудачи подряд, которые ещё могут стать разрывом, не учитываются, пока не решено. Найдено тестами: иначе после разрыва панель минуту показывала бы «нестабильно», а перед «частично» мелькало бы «нестабильно».

### 17. Цветной значок в строке меню
- Строка меню перекрашивает обычные значки в один цвет, поэтому значок собирается как `NSImage` с `NSImage.SymbolConfiguration(paletteColors:)` и `isTemplate = false` (AppKit, macOS 12+). Форма своя для каждого состояния (`wifi`, `wifi.exclamationmark`, `wifi.slash`), чтобы различалось и без цвета.

### 18. Значок приложения рисуется скриптом
- `scripts/make-app-icon.swift` (команда `make icon`): свой рисунок волн, без SF Symbols (их лицензия запрещает использование в значках приложений). Фон сплошной на весь квадрат: по имеющимся сведениям, macOS 26 сама скругляет такие значки. **Не проверено на экране** — оценивает владелец.

## 2026-11-06 — этап 3, «Уведомления»

### 20. Правила уведомлений (`NotificationPolicy`, 15 тестов)
- «Интернет пропал» и «вернулся» (с длительностью от начала разрыва) — всегда. Повторных «пропал» внутри одного разрыва нет, даже если между неудачами мелькнуло «проверяю».
- «Связь нестабильна» — при входе в это состояние, не чаще раза в 10 минут; отключается в настройках (решение владельца — включено по умолчанию).
- «Часть сайтов недоступна» — не чаще раза в 10 минут; «Все сайты снова доступны» (решение владельца) — только если было «недоступны».
- Пока с запуска приложения не было работающего интернета — уведомлений нет: при входе в систему Wi-Fi часто подключается позже приложения.
- Несколько событий сразу (например, «вернулся» и «часть сайтов недоступна») отправляются по порядку одной задачей.

### 21. Настройки применяются сразу и проходят ту же проверку, что при запуске
- Изменение → `MonitorSettings.validated(from: asStoredValues)` → сохранение в UserDefaults → `ConnectivityEvaluator.update(settings:)`. Новые пороги действуют на уже накопленную статистику, новая частота — со следующей паузы.
- Пределы значений — одна функция `MonitorSettings.allowedRange(for:)` и для окна настроек, и для проверки при запуске (тест «одни и те же диапазоны»).

### 22. Окно настроек — стандартная сцена `Settings`
- Открывается кнопкой в панели: `NSApp.activate()` (macOS 14+, старый `activateIgnoringOtherApps` устарел) и `openSettings` (macOS 14+). Сверено по AppKit/SwiftUI в SDK 26.5.

## 2026-11-06 — этап 4, «IP и VPN»

### 23. Признак VPN — туннельный интерфейс с IPv4-адресом
- У системных туннелей macOS (`utun0`–`utun3` и др.) только локальный IPv6; у VPN владельца — `utun4` с IPv4 из 198.18.0.0/15. Префиксы туннелей: `utun`, `ipsec`, `ppp`, `tun`, `tap`, `wg`. Адрес 169.254.x.x (без сети) не считается. Логика — `NetworkAddresses`, тесты.
- Интерфейсы читаются системной функцией `getifaddrs`. `String(cString: [CChar])` устарел в Swift 6 — используется `String(decoding:as:)`, как советует компилятор.

### 24. Локальный IP — IPv4 на основном интерфейсе
- Основной интерфейс (Wi-Fi или кабель) берётся из `NWPath.availableInterfaces` (`name`, `type`); если его нет — первый `en*`. Петля и 169.254.x.x не показываются.

### 25. Внешний IP — только HTTPS, строгий разбор, раз в минуту
- Россия: Яндекс (`ipv4-internet.yandex.net`, запасной `yandex.ru/internet`); зарубеж: ipify, icanhazip, Amazon checkip. По простому HTTP служба Яндекса через VPN владельца отвечала «127.0.0.1» — поэтому HTTPS.
- Ответ — не больше 64 байт и строго IPv4/IPv6 (`IPAddressText`, системная `inet_pton`); иначе «не удалось узнать». Тот же разбор теперь проверяет ответ Яндекса в проверке связи.
- Раз в минуту, сразу при смене VPN/локального IP и после возвращения интернета; без интернета внешний IP не показывается (старый был бы неправдой).

### 26. Правила уведомлений об адресах (`AddressPolicy`, 11 тестов)
- «VPN включён/отключён» — когда новое состояние держится 10 с (при переподключении VPN «мигает»); отсчёт заново после каждого мигания.
- Смена внешнего IP в течение 2 минут после изменения VPN объясняется VPN — отдельного уведомления нет.
- О смене IP одного региона — не чаще раза в 10 минут; «было» — последний известный адрес. «Не удалось узнать» — не смена. При запуске — без уведомлений.
- IP-адреса показываются в панели и в уведомлениях, но не пишутся в журнал.

## 2026-11-06 — этап 5, «Сервер в Нидерландах»

### 27. Сервер проверяется напрямую через Wi-Fi/кабель, в обход VPN
- Обычным путём VPN владельца «открывает» соединение с любым адресом (решение 13). С привязкой к физическому интерфейсу (`NWParameters.requiredInterface`) ответы честные. Проверено и скриптом на Python (`IP_BOUND_IF`), и Network.framework: `192.0.2.1` — нет ответа, Яндекс — 8 мс, имя `ya.ru` — 17 мс.
- Интерфейс — первый Wi-Fi или кабель из `NWPath.availableInterfaces`.

### 28. Без ping (решение владельца)
- В приложении ответ на ping не принимается: журнал песочницы — `deny(1) network-inbound`, `recvfrom` возвращает «нет разрешения». Для ping нужно разрешение на входящие соединения (`com.apple.security.network.server`) — права не расширяем.
- Способы: «автоматически» — TCP-порты 443, затем 22; «только мой порт».

### 29. Правила для сервера (`ServerEvaluator`, `ServerPolicy`, `ServerProbePlan` — 25 тестов)
- Раз в 15 с (решение владельца); при подозрении — через 1 с; таймаут 1 с; первым — способ, сработавший в прошлый раз (при живом сервере — одно соединение).
- «Не отвечает» — после `failuresBeforeOutage` неудач подряд, и только пока домашний интернет работает; без интернета — «нет интернета — не проверить», неудачи не копятся.
- Уведомления: «не отвечает» (не чаще раза в 10 минут), «снова отвечает» с длительностью (решение владельца) — только если было «не отвечает»; пропажа интернета посреди сбоя сервера историю не прерывает; с запуска, пока сервер ни разу не ответил, — молчим.
- После смены адреса, способа или порта история сервера начинается заново.

### 30. Адрес сервера — строго проверяется и не пишется в журнал
- IPv4/IPv6 или имя по RFC 1123 (части 1–63 символа, латиница, цифры, дефис не по краям, всего до 253). Неверный адрес в хранилище → пусто и запись «неверное значение» без самого адреса.
- В хранилище настроек появились строки (`StoredValue.string`); числа и «вкл/выкл» по-прежнему не путаются со строками.
- «Вернуть значения по умолчанию» не стирает адрес и способ проверки сервера.

## 2026-11-06 — исправление: ложное «Связь нестабильна» при запуске

### 33. Для «нестабильно по потерям» нужно не меньше двух потерянных проверок
- **Что было:** в 21:30 через 8 секунд после запуска пришло «Связь нестабильна, потери 17 %», через 10 секунд состояние вернулось в «работает». Самый первый запрос не дождался ответа (соединение ещё открывалось), а о качестве судим уже после 6 проверок: 1 из 6 = 17 % > порога 10 %.
- **Решение:** `ConnectivityEvaluator.minimumLostChecksForInstability = 2` — одна потеря никогда не «нестабильность». Порог 10 % работает как задумано на полной минуте проверок.
- **Защита:** тест «Одна потерянная проверка — не нестабильность, даже сразу после запуска» (повторяет сценарий) и тест «Две потерянные проверки и потери выше порога — нестабильно»; контрольные поломки (1 и 3 вместо 2) пойманы.
- **Альтернативы:** судить о качестве не раньше 12 проверок — не спасает при пороге меньше 10 %, который можно выставить в настройках; не считать первую проверку после запуска — не помогает после пробуждения Mac.

### 34. Ваш IP — напрямую в обход VPN; внешний IP — только публичный адрес (решение владельца)
- **Что было:** обе службы Яндекса (`ipv4-internet.yandex.net`, `yandex.ru/internet`) отдают `127.0.0.1` — и обычным путём, и напрямую через Wi-Fi (проверено 2026-11-06, ответ по HTTPS с настоящим сертификатом Яндекса). Утренний хэш ответа `7b8fa7` — это хэш `127.0.0.1`: строка «Внешний IP · Россия» с этапа 4 показывала петлю. Проверка этапа 4 сверяла только вид адреса и его хэш, а не смысл. Поймала это проверка страны: ipinfo ответил «bogon address», ipapi — `Undefined`.
- **Решение:** ваш IP узнаётся у ipify / icanhazip / Amazon **напрямую через Wi-Fi/кабель** (`NWParameters.tls` + `requiredInterface`; URLSession привязываться к интерфейсу не умеет). Строка — «Ваш IP · напрямую»: при раздельной настройке VPN это адрес, который видят российские сайты. Зарубежный IP — как раньше, обычным путём.
- **Защита:** `IPAddressText.isPublic` — внешний IP только публичный (14 зарезервированных диапазонов IPv4, у IPv6 — только 2000::/3 без 2001:db8::/32); служебный ответ → «не удалось узнать». `DirectHTTP` — сборка запроса HTTP/1.0 и строгий разбор ответа (код, длина, без «chunked»). Всё — тестами и контрольными поломками.
- **Яндекс** остаётся только в проверке связи «Россия»: там важно, что сервер ответил, а не какой адрес он назвал.
- **Альтернатива:** искать другой российский сервис — отклонена владельцем: нет гарантии надёжности.

### 35. Службы IP и стран не должны связывать ваш домашний IP с VPN-сервером (проверка свежим взглядом)
- **Что нашла проверка:** страну вашего домашнего IP спрашивали через VPN — ipinfo и ipapi получали ваш домашний IP в адресе запроса, а сам запрос — с IP VPN-сервера. Вдобавок ipify, icanhazip и Amazon раз в минуту получали два запроса в одну секунду — напрямую и через VPN — с редкой подписью «IPCHEK». По этим признакам служба может связать домашний IP с VPN-сервером. Владелец согласовал только то, что службы знают домашний IP.
- **Решение:**
  - о стране вашего IP спрашиваем напрямую (тем же путём, каким узнали сам IP): служба видит запрос с того же адреса, о котором её спрашивают;
  - службы IP разведены: напрямую — icanhazip, через VPN — ipify; Amazon — запасная для обоих (её спрашивают, только когда основная молчит);
  - подпись запросов — обычная `Mozilla/5.0` вместо «IPCHEK» (иначе URLSession подписывает запросы именем приложения);
  - страну вашего IP и IP VPN спрашиваем не ближе минуты друг к другу (`CountryPlan.staggerSeconds`), первой — зарубежную: её называет уведомление о VPN.
- **Что остаётся:** ipinfo и ipapi получают два запроса (о каждом адресе — с него же) с промежутком от минуты — при запуске и раз в сутки. Связать их можно лишь по времени, и это намного слабее прежнего. Убрать совсем — только если у двух адресов будут разные службы стран (четыре службы вместо двух); отложено, без согласия владельца новые службы не добавляем.
- **Попутно по той же проверке:**
  - после смены VPN внешний IP узнаётся сразу и ещё раз через 5 секунд (`AddressPlan.settleSeconds`): сразу после смены маршруты бывают старыми, и уведомление «VPN включён» называло прежнюю страну;
  - если уведомление о VPN всё же ушло с другой страной или без неё — верная страна приходит отдельным уведомлением; раньше её глушило правило «2 минуты после смены VPN»;
  - ответ служб дальше предела не читается (`BoundedBody`), раньше URLSession дочитывал его целиком;
  - путь в запросе в обход VPN — в закодированном виде (`percentEncodedPath`): «%0D%0A» не превращается в новую строку запроса.
- **Альтернатива:** оставить страну вашего IP через VPN — отклонена: именно это давало службам связку «домашний IP ↔ VPN-сервер».

## 2026-11-07 — установка в «Программы» раньше этапа 7

### 36. Команда `make install` — сейчас, а не на этапе 7 (просьба владельца)
- **Почему:** после включения Mac приложения не было — оно запускалось только из папки сборки, и для запуска владельцу приходилось обращаться к Claude.
- **Решение:** `make install` собирает финальную версию (`com.lavmoviesstudio.ipchek`), закрывает установленную копию, кладёт новую в `/Applications/IPCHEK.app` (`ditto`), проверяет подпись (`codesign --verify --strict`) и запускает. Отладочную IPCHEK Dev команда не трогает.
- **Закрытие установленной копии** — сигналом `pkill` по пути `/Applications/IPCHEK.app/...`: просьба «завершиться» через AppleScript потребовала бы у владельца отдельного разрешения macOS на управление приложениями. Пока приложение ничего не хранит, это безопасно; на этапе 6 (история) пересмотреть, чтобы не терять незаписанное.
- **Не сделано:** автозапуск при входе, значок в Dock, открывающий панель, перезапуск после сбоя, работа при сне — остаются в этапе 7.
- **Альтернатива:** ждать этапа 7 — отклонена: владелец без этого не может пользоваться приложением.

## 2026-11-07 — этап 7, «Автозапуск, сон, установка»

### 38. Автозапуск и перезапуск после сбоя — файл launchd в `~/Library/LaunchAgents` (решение владельца)
- **Что сделано:** `make install` кладёт файл задания `~/Library/LaunchAgents/com.lavmoviesstudio.ipchek.autostart.plist` (шаблон — `scripts/autostart.plist`, команда — `scripts/autostart.sh`) и запускает IPCHEK через launchd. launchd запускает рабочую версию при входе в систему (`RunAtLoad`) и после сбоя (`KeepAlive` → `SuccessfulExit = false`, через ~1–10 с). Штатный выход — «Выйти», выключение Mac, сигнал SIGTERM — даёт код 0, его launchd не перезапускает.
- **Переключатель в настройках IPCHEK** хранит выбор человека (по умолчанию — включено, паспорт, раздел 17). «Песочница» не даёт приложению менять файлы вне своей папки, поэтому файл задания остаётся, а копия, которую запустила macOS при выключенном переключателе, сразу штатно выходит. Второй, системный переключатель — Системные настройки → Основные → Объекты входа; состояние файла IPCHEK читает через `SMAppService.statusForLegacyPlist` (работает из «песочницы», проверено) и показывает подсказку.
- **Кто запустил процесс** — по переменной окружения `IPCHEK_LAUNCHED_BY=agent` из файла задания (`LaunchSource`). Запущенный человеком IPCHEK показывает окно, запущенный macOS — нет.
- **Почему не `SMAppService` (штатный способ Apple, был в паспорте):** при подписи без Apple ID macOS привязывает задание к отпечатку конкретной сборки. Проверено 2026-11-07: первая регистрация работает, после `make install` задание не запускается (`job state = spawn failed`, код 78 `EX_CONFIG`, `needs LWCR update`), и ни перерегистрация, ни новый номер сборки не помогают. Это известное ограничение: инженер Apple на форумах разработчиков пишет, что с подписью «Sign to Run Locally» будут такие проблемы; в других проектах задание ломалось и после перезагрузки. Файл с обычным путём к программе такой привязки не имеет — так устроен автозапуск у Homebrew, postgres и Google на этом же Mac.
- **Альтернативы, которые предлагались владельцу:** подпись бесплатным Apple ID (штатный способ остаётся, но нужен вход в Xcode и продление сертификата раз в год; меняет решение 4); только запуск при входе без перезапуска после сбоя (`SMAppService.mainApp`).
- **Ограничение:** если закрыть IPCHEK кнопкой «Выйти» и запустить снова вручную (Dock, Spotlight), эта копия работает не под присмотром launchd: перезапуск после сбоя заработает со следующего входа в систему или `make install`. «Песочница» не даёт приложению попросить launchd о запуске (BACKLOG).
- **Попытка со `SMAppService` убрана целиком:** задание снято через сам `SMAppService` (`unregister`), в базе «Объектов входа» (`sfltool dumpbtm`) остался только файл `…autostart.plist`.

### 39. `make install`: штатное закрытие вместо обрыва (пересмотр решения 36)
- Копию под присмотром launchd закрывает `launchctl bootout`, остальные — `scripts/stop-app.sh` (SIGTERM и ожидание выхода до 10 с; если не закрылась — установка останавливается).
- IPCHEK обрабатывает SIGTERM как «Выйти» (`DispatchSource` → `NSApp.terminate`): выход с кодом 0, launchd не принимает его за сбой, а с этапа 6 история успеет записаться.
- Процессы ищутся по идентификатору приложения (`lsappinfo`), а не по пути: launchd запускает программу с коротким путём в командной строке, и прежний `pkill -f '^/Applications/…'` её не находил (замечено при проверке).
- Если автозапуск выключен (в IPCHEK или в Системных настройках), `scripts/autostart.sh start` через 3 с видит, что IPCHEK не работает, и запускает его обычным способом.

### 40. Сон Mac: пауза без тревог и минуты сна не в счёт (`SleepGuard` и др., 29 тестов)
- Сообщения macOS о сне и пробуждении (`NSWorkspace.willSleep/didWake`). Пока Mac спит и ещё `wakeGraceSeconds` после пробуждения (30 с, паспорт), правила уведомлений не спрашиваются. В конце паузы приложение показывает им текущее состояние ещё раз: интернета так и нет — придёт «пропал», вернулся — тишина. VPN, не вернувшийся за паузу, и новый IP тоже придут уведомлением: правила сравнивают с тем, что было до сна.
- После пробуждения оценка связи и сервера начинается заново («проверяю» с момента пробуждения, статистика за минуту до сна забыта), проверки, начатые до сна, не учитываются, проверка — сразу.
- Минуты сна не входят в длительность в «вернулся», «снова доступны», «сервер снова отвечает»: начало открытой истории сдвигается на время сна. Конец истории — момент, когда состояние сменилось, а не когда приложение это заметило (после паузы — разница до 30 с).
- Пауза настраивается в окне настроек («После пробуждения Mac молчать», 0–300 с).
- **Проверено** тестами, включая сценарии «крышка закрыта 10 минут», «проснулся без интернета», «проснулся без Wi-Fi», «разрыв до сна». На настоящем сне Mac — проверяет владелец (критерий этапа).

### 41. Пропажа Wi-Fi или кабеля — уведомление через 5 секунд (решение владельца)
- Значок краснеет сразу, а уведомление «Интернет пропал» по пропаже Wi-Fi/кабеля приходит, только если они не вернулись за 5 секунд (`NotificationPolicy.linkLossConfirmSeconds`, 6 тестов). Смена сети и короткие провалы — без тревоги и без «вернулся, не было 3 с». Длительность разрыва считается с момента пропажи.
- Без Wi-Fi проверки не идут, поэтому подтверждение наступает по таймеру (`recheckAt`).
- Было (паспорт, разделы 4 и 11): уведомление через 1–2 с. Альтернатива «сразу, как было» — отклонена владельцем.

### 42. Значок в Dock — только для запуска; клик по нему открывает окно состояния (решение владельца)
- IPCHEK остаётся приложением строки меню (`LSUIElement`): под значком в Dock нет точки, в ⌘Tab его нет. Значок в Dock — закреплённый владельцем ярлык.
- Клик по значку (а также Spotlight, Launchpad), когда IPCHEK работает, — `applicationShouldHandleReopen`: открывается окно с той же панелью, что в строке меню. Запуск вручную тоже показывает это окно (решение владельца); запуск при входе и после сбоя — без окна.
- Окно — `NSWindow` с той же SwiftUI-панелью: открыть панель строки меню программно в SwiftUI нельзя. Кнопка «Настройки» из окна работает (проверено).
- Альтернатива «как обычное приложение» (точка под значком, ⌘Tab, меню вверху) — отклонена владельцем.
