# Инженерный стандарт проекта

Этот файл не загружается автоматически. Claude читает его при планировании и перед каждым этапом — только активные модули и раздел «Готово».

Модуль применяется, если он отмечен в паспорте проекта (`docs/PROJECT.md`) как активный. Пункт, который к проекту не подходит, не реализуй ради галочки: запиши в паспорте, почему он неприменим. Если продукт не подходит ни под один специальный модуль (например, десктоп-приложение или браузерное расширение), применяй А, Б, В и Р и опиши в паспорте риски этой платформы.

Опорные источники: OWASP Top 10:2025, OWASP Top 10 для LLM-приложений (2025), WCAG 2.2, принципы Twelve-Factor App, практики SRE.

## А. Основа

- Слои: интерфейс → обработчики запросов → бизнес-логика → доступ к данным. Бизнес-логика не живёт в компонентах интерфейса.
- Валидация входных данных и проверка прав — только на сервере, в каждой точке входа. Клиенту не доверяем ни в чём.
- Проверка доступа — одна общая функция, без копий логики.
- Идентификаторы ресурсов неугадываемые (UUID), но это не замена проверке прав.
- Единый формат ошибок и единый обработчик: человеку — понятное сообщение, в лог — подробности с идентификатором запроса. Стектрейсы наружу не уходят.
- Конфигурация — только через переменные окружения, которые проверяются при старте. С неверной конфигурацией приложение не запускается. `.env.example` всегда актуален.
- Окружения разделены: у разработки и прода свои переменные, ключи и базы. Окружения максимально похожи друг на друга, чтобы ошибка проявлялась ещё в разработке.
- Строгая типизация, линтер, форматтер, проверка перед коммитом.
- Мелкие модули, понятные имена, никакого дублирования логики.
- Время хранится в UTC, показывается в часовом поясе пользователя.
- Версии продукта нумеруются, изменения записываются в `CHANGELOG.md`.

## Б. Безопасность

- **Доступ (OWASP A01).** Права проверяются на сервере для каждого ресурса. По умолчанию — запрет: доступ открывается явно. CSRF: SameSite-cookie плюс проверка `Origin` на изменяющих запросах.
- **Ошибка — это отказ (A10).** Если проверка прав, подписи или внешнего сервиса упала или не ответила, операция отклоняется, а не пропускается. Никаких `catch`, после которых выполнение идёт дальше как ни в чём не бывало.
- **Настройки (A02).** Отладочный режим, тестовые учётки и подробные ошибки в проде выключены. Заголовки: CSP, HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, `frame-ancestors`.
- **Цепочка поставок (A03).** Lock-файл в репозитории, установка строго по нему. Каждый пакет проверен на существование и репутацию до установки. Минимум зависимостей. Аудит без high/critical, автообновления. Действия в CI закреплены на конкретных версиях.
- **Криптография (A04).** Только стандартные проверенные библиотеки, HTTPS везде, никакого самописного шифрования.
- **Инъекции (A05).** SQL — только через ORM или параметризованные запросы. XSS — данные пользователя выводятся только как текст, HTML из пользовательского ввода не вставляется. Никакого выполнения команд оболочки с пользовательским вводом.
- **Проектирование (A06).** Угрозы из паспорта учтены в архитектуре: лимиты, роли, что будет при злоупотреблении.
- **Целостность (A08).** Входящие вебхуки проверяются по подписи. Данные, которые пришли от клиента, не считаются доверенными, даже если их сформировал наш же фронтенд.
- **Журнал безопасности (A09).** Логируются входы, неудачные попытки, отказы в доступе, действия админа. На всплеск таких событий приходит оповещение.
- **CORS:** только явно разрешённые origin, никакого `*` вместе с credentials.
- **SSRF:** сервер не ходит по ссылкам от пользователя. Если без этого никак — белый список и запрет внутренних адресов.
- **Открытые редиректы:** параметры вида `?next=` принимают только внутренние пути.
- **Секреты:** только в окружении, `.env*` в `.gitignore`, в клиентский код ничего секретного не попадает, в CI работает сканер секретов. В `docs/OPERATIONS.md` описано, как сменить каждый ключ, если он утёк.
- **Минимальные права:** пользователь БД приложения — не суперпользователь; ключ хранилища даёт доступ только к своему бакету; у каждого окружения свои ключи.
- **Rate limiting** на всех точках входа, жёстче — на вход, загрузку и отправку писем. Учитывай реальный IP за прокси (подделка `X-Forwarded-For` не должна обходить лимит) и то, что лимитер, который хранит состояние в памяти процесса, не работает при нескольких экземплярах приложения.
- **Сообщения об уязвимостях:** файл `/.well-known/security.txt` с контактом, куда сообщать о найденных уязвимостях.
- **Злоупотребления:** формы защищены от ботов (скрытое поле-ловушка или капча), письма на непроверенные адреса не рассылаются массово, есть лимиты на размер запросов, количество объектов и длину строк.

## В. Слепые зоны ИИ-кода

То, что ИИ-агенты пропускают чаще всего. Проверяй после каждого этапа.
1. **Ограничения только в интерфейсе.** Каждое правило интерфейса повторно проверяется на сервере.
2. **Защита не в той точке.** Middleware и layout не защищают обработчики. Next.js: каждая server action и каждый route handler — публичный HTTP-эндпоинт, проверка сессии и прав нужна внутри каждого.
3. **Mass assignment.** Схемы валидации пропускают только разрешённые поля. `ownerId`, `role`, `quota`, `status` и подобные поля от клиента не принимаются.
4. **Утечка через сериализацию.** В ответы API и клиентские компоненты не уходят хэши паролей, токены, чужие данные и служебные поля.
5. **Общий кэш с персональными данными.** Страницы и запросы с данными пользователя не кэшируются статически и не попадают в общий кэш.
6. **Потерянные промисы.** Включено правило `no-floating-promises` или его аналог, необработанных rejection нет.
7. **Тесты, которые ничего не проверяют.** Тест, который зелёный при сломанном коде, — дефект. Важные проверки (доступ, лимиты) подтверждай контрольной поломкой, которую сразу откатываешь, а затем по `git diff` убеждаешься, что откат сделан.
8. **Только счастливый путь.** Пустые данные, граничные значения, двойной клик, отмена, обрыв сети, параллельный вызов.
9. **GET, который меняет данные.** Выход, удаление, подтверждение — никогда не по GET. Ссылка из письма открывает страницу с кнопкой, а действие выполняется POST-запросом. Иначе боты предпросмотра в мессенджерах и почтовые сканеры откроют ссылку раньше человека и сожгут одноразовый токен.
10. **Большие данные целиком в памяти.** Файлы и выгрузки обрабатываются потоками.
11. **Фоновые задачи, которые работают только в тестах.** В прод-сборке задачи запускаются сами по расписанию, а повторный запуск ничего не дублирует.
12. **Работает в режиме разработки — ломается в проде.** Проверяй production-сборку.
13. **Выдуманные пакеты.** Имя пакета, которое «вспомнилось», проверяется в реестре до установки: существует ли, давно ли, много ли загрузок, тот ли автор.
14. **Ошибка открывает дверь.** `try/catch` вокруг проверки прав или подписи, после которого код продолжает работу, — это обход защиты. При любой ошибке проверки — отказ.

## Г. Аккаунты и доступ

- Авторизация — проверенная поддерживаемая библиотека, никакой самописной криптографии. Если пароли храним сами — Argon2id, минимальная длина и, желательно, проверка по базе утёкших паролей.
- Cookie сессии: `HttpOnly`, `Secure`, `SameSite`. Новый идентификатор сессии при входе, полная инвалидация при выходе и смене пароля (на всех устройствах).
- Лимит попыток входа и сброса пароля.
- Существование email не раскрывается ни текстом ответа, ни временем ответа.
- Токены сброса и подтверждения — одноразовые, короткоживущие, хранятся в виде хэшей.
- Смена пароля и email требует текущего пароля. Новый email начинает работать после подтверждения, на старый приходит уведомление.
- Каждый запрос к ресурсу проверяет владельца на сервере, чужой ресурс → 404. Тесты: пользователь B ничего не может сделать с данными пользователя A ни через один эндпоинт.
- Удаление аккаунта удаляет все данные пользователя, включая файлы.
- Команды и организации (если есть): доступ проверяется по членству и роли в организации, данные разных организаций изолированы друг от друга.
- Соединения реального времени (WebSocket и аналоги) проверяют сессию при подключении и права на каждый канал и каждое сообщение.

## Д. Файлы

- Загрузка — напрямую в объектное хранилище по коротким подписанным ссылкам, после проверки прав и квоты. Крупные файлы — multipart с докачкой. В хранилище — правило автоудаления незавершённых загрузок.
- Ключ объекта в хранилище — случайный, никогда не имя файла.
- Размер и квота проверяются дважды: при выдаче ссылки и по фактическому размеру после загрузки (подписанный PUT размер сам не ограничивает).
- Тип файла определяется по содержимому (magic bytes), а не по расширению. Разрешённые типы — белым списком.
- Отдача файла: `attachment` и безопасный тип. Если файл отдаётся прямо из хранилища, тип и `Content-Disposition` задаются параметрами подписи, а домен хранилища отличается от домена приложения. SVG и HTML никогда не открываются внутри страницы основного домена.
- Имена: кириллица в `Content-Disposition` через `filename*=UTF-8''`, нормализация NFC, запрет управляющих символов, `/`, `\` и символа U+202E, лимит длины в байтах.
- Размер файла — BIGINT. Единицы размера (1000 или 1024) одинаковы во всём продукте.
- Одинаковые имена в одной папке: заранее выбранное правило (запрет или `файл (1).jpg`) плюс уникальный индекс в БД.
- Приватные файлы и подписанные ссылки не кэшируются: `Cache-Control: private, no-store`.
- Превью: лимит на число пикселей, генерация в фоне, удаление EXIF и GPS.
- Нужна ли антивирусная проверка загрузок — решает человек; если да, она идёт в фоне до выдачи файла другим людям.
- Согласованность БД и хранилища: запись `pending` → загрузка → проверка → `ready`. Объекты-сироты чистит фоновая задача. Удаление: мягкое → корзина → физическое удаление в фоне.
- Ссылки доступа (если есть): длинный случайный токен, срок действия, отзыв, `noindex`.

## Е. Админка и роли

- Роль проверяется на сервере в каждом админском обработчике. Скрытая ссылка и закрытая страница — не защита.
- Роль берётся из актуальных данных. Снятие роли и блокировка сразу действуют на уже открытые сессии.
- Повысить себе права нельзя ни через один эндпоинт.
- Никаких бэкдоров: паролей по умолчанию, захардкоженных email с особыми правами, отладочных эндпоинтов. Первый админ создаётся процедурой, описанной в `docs/OPERATIONS.md`.
- Двухфакторный вход для админа, повторное подтверждение перед опасными действиями.
- Данные пользователей в админке выводятся только как текст: XSS против админа — самое опасное место продукта.
- Журнал всех действий админа, который нельзя изменить из админки.
- Доступ к содержимому чужих файлов — только если он действительно нужен, и каждый раз с записью в журнал.
- Нельзя удалить или разжаловать последнего админа. Массовые операции ограничены по размеру и идемпотентны.
- Ввод в админке проходит такую же строгую валидацию, как у пользователей: аккаунт админа тоже могут украсть. Списки по всем пользователям пагинируются.
- Вход под пользователем (если есть): пишется в журнал, в интерфейсе виден баннер «вы вошли как …», выход возвращает в сессию админа, в этом режиме нельзя менять роли и пароли.
- Экспорт в CSV: ячейки, начинающиеся с `=`, `+`, `-`, `@`, экранируются; кодировка UTF-8 с BOM, чтобы кириллица открывалась в Excel.

## Ж. Платежи

- Суммы хранятся в минимальных единицах (копейки, центы) целыми числами, а не дробными.
- Сумму и состав покупки определяет сервер, а не клиент.
- Статус оплаты меняется только по уведомлению платёжного сервиса — с проверкой подлинности (подпись или повторный запрос статуса к API сервиса), а не по редиректу «оплата успешна».
- Уведомления обрабатываются идемпотентно: повтор не начисляет дважды. При создании платежа используются ключи идемпотентности.
- Продуманы возвраты, отмены и неоплаченные заказы.
- До запуска — тестовый режим платёжного сервиса. Боевые ключи живут только в окружении прода.
- При продажах в России нужны онлайн-чеки (54-ФЗ): выясни, как их формирует выбранный сервис.
- В мобильных приложениях правила магазина о цифровых покупках проверь до проектирования оплаты.

## З. Персональные данные и закон

- Собираем минимум данных. Для каждого поля известно, зачем оно нужно.
- Есть согласие на обработку, политика конфиденциальности и возможность удалить аккаунт со всеми данными.
- Определены сроки хранения: логи и бэкапы удаляются по расписанию, и данные удалённого пользователя со временем исчезают и из них.
- Пользователи из России: 152-ФЗ — согласие оформляется отдельным документом, оператор уведомляет Роскомнадзор, данные россиян хранятся на серверах в России. Передача персональных данных зарубежным сервисам (аналитика, нейросети, почта) — трансграничная передача, о ней тоже нужно отдельно уведомлять. Штрафы за утечки с 2025 года выросли кратно.
- Пользователи из ЕС: GDPR.
- Баннер cookie, если используются аналитика или трекеры.
- Тексты юридических документов — заготовка. Скажи человеку, что финальную версию должен проверить юрист.

## И. Интерфейс и дизайн

- Референсы в `design/` — источник истины. Значения, снятые с картинки, — ориентиры: подгоняй по картинке. Чужие ассеты (фото, иллюстрации, логотипы) не копируй.
- Экраны, которых нет на референсе, делай в том же визуальном языке и согласуй с человеком до вёрстки.
- Сверка: скриншоты на ширинах 1440, 768 и 390 px (например, через Playwright), сравнение с референсом, список расхождений, исправление. Итоговые скриншоты — эталоны для визуальных тестов.
- У каждого экрана есть состояния: загрузка (без скачков вёрстки), пусто, ошибка с повтором, нет сети. Оптимистичные обновления — только с откатом при ошибке.
- Нет утечек на клиенте: временные ссылки на файлы освобождаются (`URL.revokeObjectURL`), подписки снимаются, запросы отменяются при уходе со страницы (`AbortController`).
- Адаптив: safe areas, `dvh` вместо `vh` на мобильных, шрифт в полях ввода не меньше 16px (иначе iOS увеличивает страницу), ничего важного не доступно только по наведению.
- Доступность по WCAG 2.2, уровень AA: работа с клавиатуры, видимый фокус, `aria-label` у кнопок-иконок, контраст текста не ниже 4.5:1, нажимаемые элементы не меньше 24×24 px, `prefers-reduced-motion`, модалки удерживают фокус и закрываются по Escape.
- Скорость (Core Web Vitals): LCP до 2,5 с, INP до 200 мс, CLS до 0,1. Анимируются только `transform` и `opacity`, изображения в AVIF/WebP с заданными размерами, длинные списки виртуализированы, шрифты загружаются без мигания.
- Тексты: кнопка называет действие, ошибка говорит, что делать, пустое состояние предлагает действие. Склонения — через `Intl.PluralRules` (1 файл, 2 файла, 5 файлов). Длинные имена обрезаются, не ломая вёрстку.
- Браузеры: Chromium, Firefox и WebKit (Safari).

## К. Данные и БД

- Ограничения в схеме: внешние ключи с осознанным `ON DELETE`, `NOT NULL`, уникальные индексы, `CHECK`.
- Многошаговые записи — в транзакциях.
- Индексы под частые запросы, курсорная пагинация, никаких N+1.
- Деньги и размеры — целые числа, большие значения — BIGINT. Время — `timestamptz` в UTC.
- Миграции версионируются. Уже применённые миграции не редактируются. Перед миграцией в проде — бэкап. Разрушающие изменения схемы (удаление и переименование колонок) делаются в два шага, чтобы старая и новая версии приложения работали одновременно.
- Тестовые данные (сиды) никогда не попадают в прод.
- Гонки (двойные отправки, параллельные изменения) закрыты уникальными ограничениями, транзакциями и ключами идемпотентности.
- Бэкапы с проверенным восстановлением.

## Л. Надёжность и эксплуатация

- Docker: многоэтапная сборка строго по lock-файлу, запуск не от root, healthcheck. Нативные зависимости проверяются внутри собранного образа.
- Эндпоинты `/healthz` (живость) и `/readyz` (готовность).
- Таймауты на все внешние вызовы. Повторы с экспоненциальной задержкой — только для идемпотентных операций. Если внешний сервис недоступен, продукт деградирует понятно для пользователя, а не падает целиком.
- Graceful shutdown: при остановке текущие запросы и задачи завершаются корректно.
- Логи структурированные, с идентификатором запроса, без паролей, токенов, подписанных ссылок и лишних персональных данных.
- Трекинг ошибок и мониторинг доступности с оповещением человеку.
- Фоновые задачи запускаются по расписанию и идемпотентны. Временные файлы удаляются.
- Письма: SPF, DKIM и DMARC для домена, ссылки строятся от боевого домена, у каждого письма есть текстовая версия.
- Расходы под контролем: у хостинга и платных API включены лимиты или оповещения о превышении бюджета.
- `docs/OPERATIONS.md`: как развернуть, обновить, откатить, восстановить из бэкапа, сменить утёкший ключ. После каждого инцидента — короткий разбор без поиска виноватых: что случилось, почему, что меняем.

## М. Мобильное приложение

- Токены — в Keychain (iOS) или Keystore (Android), не в обычных настройках. Секретные ключи сервисов в приложение не встраиваются: приложение можно разобрать.
- Связь с сервером только по HTTPS.
- Старые версии приложения продолжают работать после обновления сервера: API версионируется, есть механизм обязательного обновления, если старую версию поддерживать уже нельзя. Люди обновляют приложения не сразу.
- Разрешения (камера, фото, геолокация) запрашиваются в момент использования, с понятным объяснением. Если человек отказал, приложение продолжает работать.
- Жизненный цикл: сворачивание, звонок, нехватка памяти, выгрузка процесса системой — данные не теряются.
- Плохая сеть и офлайн — понятные состояния.
- Кэш и временные файлы чистятся, приложение не разрастается со временем.
- Требования магазинов: если есть регистрация — удаление аккаунта внутри приложения; для iOS — Privacy Manifest; правила о цифровых покупках; честное описание собираемых данных.
- Проверка на реальных устройствах: старая и новая версии ОС, маленький и большой экран.
- Подключены отчёты о сбоях. У каждой версии есть номер и список изменений.

## Н. Telegram

- Токен бота — только в окружении.
- Вебхук ставится с секретным токеном: Telegram присылает его в заголовке `X-Telegram-Bot-Api-Secret-Token`, запросы без него отклоняются.
- Telegram повторяет обновление, если не получил успешный ответ. Поэтому обработка идемпотентна по `update_id`, на вебхук отвечаем быстро, а долгую работу уносим в фон.
- Мини-приложение: данные пользователя (`initData`) проверяются на сервере по подписи. Без проверки им не доверяем.
- Админские команды проверяются по ID пользователя из конфигурации, а не по имени.
- Рассылки идут через очередь с учётом лимитов Telegram и корректно обрабатывают пользователей, заблокировавших бота.
- Всё, что пишет пользователь, — недоверенный ввод.

## О. ИИ-функции

По OWASP Top 10 для LLM-приложений (2025).
- **Ключи** к API нейросетей — только на сервере. Запросы к модели идут через наш бэкенд, а не напрямую из браузера или приложения.
- **Prompt injection.** Всё, что попадает в запрос к модели от пользователя или извне (документы, письма, веб-страницы), — данные, а не команды. Модель не может сама выполнить опасное действие: удаление, оплату, отправку писем, доступ к чужим данным. Такие действия проходят обычную проверку прав или подтверждение человеком.
- **Минимальные полномочия.** Инструменты и данные, доступные модели, ограничены тем, что нужно для задачи.
- **Ответ модели — недоверенный ввод.** Не вставляется как HTML и не выполняется как код или запрос к БД. Структурированный ответ проверяется по схеме.
- **Системный промт** не содержит секретов и персональных данных: считай, что пользователь его увидит.
- **Расходы.** Лимиты на пользователя (запросы, токены, размер входа), общий бюджет с оповещением, таймауты. Иначе одна атака съедает месячный бюджет за ночь.
- **Персональные данные** в запросах — по минимуму. Для пользователей из России учитывай правила трансграничной передачи (модуль З).
- Если провайдер модели недоступен, продукт работает без ИИ-функции или честно сообщает о сбое.
- Версия модели зафиксирована. Есть набор тестовых запросов для ключевых сценариев, включая попытки prompt injection, — их прогоняют при смене модели или промта.
- В логах запросов к модели нет персональных данных и секретов.

## П. Публичный сайт

- У каждой страницы свой `title` и `description`, разметка Open Graph для превью в мессенджерах, канонический адрес.
- `sitemap.xml` и `robots.txt`. Приватные страницы закрыты от индексации.
- Семантическая вёрстка: один `h1`, правильные уровни заголовков, `alt` у изображений.
- Аналитика считает события из критерия успеха в паспорте, подключается с учётом согласия на cookie (модуль З).

## Р. Тестирование

- Юнит-тесты на бизнес-логику: права, лимиты, расчёты.
- Интеграционные тесты с настоящими БД и хранилищем (в Docker), а не на моках.
- E2E-тест на главный сценарий из паспорта.
- Тесты безопасности по активным модулям: доступ к чужим данным, роли, опасные файлы, XSS в пользовательских полях, лимиты.
- Тесты на сбои: недоступна БД или внешний сервис — продукт ведёт себя предсказуемо и не открывает доступ.
- Тесты стабильны: проходят три раза подряд.
- Независимые инструменты, которые ошибаются иначе, чем ИИ: статический анализ кода (например, Semgrep) в CI и сканирование запущенного приложения на типовые уязвимости (например, ZAP в базовом режиме) перед релизом.
- CI: lint → typecheck → тесты → сборка → аудит зависимостей → статический анализ → сканер секретов. Слияние только при зелёном CI.
